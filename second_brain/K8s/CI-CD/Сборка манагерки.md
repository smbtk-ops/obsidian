# Jenkins сборки back-mgmnt stage и maxline-manager

## 1. Назначение

Документ описывает две Jenkins-сборки:

| Сборка | Репозиторий | Образ | Назначение |
|--------|-------------|-------|------------|
| `back-mgmnt-stage` | `git@bitbucket.org:maxlinecode/maxlineby.git` | `nexus.maxline.by/docker-images-hosted/back-mgmnt-stage:<tag>` | PHP/Phalcon backend `back-mgmnt` для namespace `stage` |
| `maxline-manager` | `git@bitbucket.org:maxlinecode/maxline-manager.git` | `nexus.maxline.by/docker-images-hosted/maxline-manager:<tag>` | React/Vite manager frontend для Kubernetes |

Обе сборки:

- берут исходники из Bitbucket;
- формируют Docker tag по времени сборки, ветке и commit hash;
- логинятся в Nexus Docker registry;
- собирают Docker image;
- пушат image в Nexus;
- деплоят image в Kubernetes через kubeconfig из Jenkins credentials;
- проверяют rollout и делают rollback при неуспешном rollout.

## 2. Общие параметры и credentials

### 2.1. Registry

| Переменная | Значение |
|------------|----------|
| `REGISTRY_URL` | `nexus.maxline.by` |
| `REGISTRY_REPO` | `docker-images-hosted` |
| `REGISTRY_CREDENTIALS` | `nexus-docker-creds` |

Итоговый формат образа:

```text
nexus.maxline.by/docker-images-hosted/<IMAGE_NAME>:<IMAGE_TAG>
```

### 2.2. Kubernetes

| Переменная | Значение |
|------------|----------|
| `KUBECONFIG_CRED` | `kube_config` |
| Rollout timeout | `300s` |

Jenkins получает kubeconfig как file credential и перед деплоем выставляет:

```bash
export KUBECONFIG=$KUBECONFIG_FILE
```

### 2.3. Docker tag

В обеих сборках tag строится одинаково:

```text
dd-MM-yyyy-HH-mm-ss-<branch-name>-<short-commit-hash>
```

Пример:

```text
04-05-2026-15-20-11-main-a1b2c3d
```

Слэши в имени ветки заменяются на дефисы:

```text
feature/test -> feature-test
```

## 3. Сборка `back-mgmnt-stage`

### 3.1. Что собирается

Сборка собирает PHP-FPM образ backend-приложения `maxlineby`.

Основной Dockerfile:

```text
app/k8s/stage/Dockerfile
```

Контекст сборки:

```text
app/
```

Итоговый image:

```text
nexus.maxline.by/docker-images-hosted/back-mgmnt-stage:<IMAGE_TAG>
```

### 3.2. Параметры Jenkins

| Параметр | Тип | Назначение |
|----------|-----|------------|
| `BRANCH` | Git branch | Ветка backend-репозитория `maxlineby` |
| `CLEAN_WORKSPACE` | Boolean | Очистить Jenkins workspace перед checkout |

### 3.3. Checkout

Сборка использует два репозитория:

| Директория в workspace | Репозиторий | Ветка |
|------------------------|-------------|-------|
| `app/` | `git@bitbucket.org:maxlinecode/maxlineby.git` | выбранная `BRANCH` |
| `envs/` | `git@bitbucket.org:maxlinecode/docker_maxline_by.git` | `master` |

Из env-репозитория копируются файлы:

```bash
cp ${WORKSPACE}/envs/app_env ${WORKSPACE}/app/.env
cp ${WORKSPACE}/envs/default_settings.php ${WORKSPACE}/app/site/backend/config/default_settings.php
```

После копирования `.env` правится под stage:

| Ключ | Значение после замены |
|------|------------------------|
| `REDIS_CACHE_HOST` | `back-mgmnt-redis.stage.svc.cluster.local` |
| `DB_HOST` | `10.10.1.38` |
| `DB_DIRECT_HOST` | в pipeline заменяется строкой `DB_HOST=10.10.1.42` |
| `DB_MASTER_HOST` | `10.10.1.38` |
| `DB_SLAVE_HOST` | `10.10.1.38` |

Важно: для `DB_DIRECT_HOST` в pipeline указана замена на `DB_HOST=10.10.1.42`, а не на `DB_DIRECT_HOST=10.10.1.42`. Если это не задумано специально, в итоговом `.env` может появиться второй `DB_HOST` вместо `DB_DIRECT_HOST`.

### 3.4. Docker build

Команда сборки:

```bash
docker build -t $REGISTRY_URL/$REGISTRY_REPO/$IMAGE_NAME:$IMAGE_TAG \
    -f app/k8s/stage/Dockerfile \
    app/
```

Dockerfile основан на:

```text
php:7.3.33-fpm
```

В образ устанавливаются:

- системные пакеты для PHP extensions и runtime-утилит;
- Composer;
- Phalcon `v3.4.5`;
- PHP extensions: `zip`, `intl`, `sockets`, `opcache`, `soap`, `gmp`, `gd`, `redis`, `rdkafka`, `pdo_mysql`, `mongodb`, `amqp`;
- Datadog PHP tracer `0.90.0`;
- зависимости Composer для `parsers/parser-fonbet-live`;
- код `site/`;
- `www.conf` для PHP-FPM;
- `k8s/php.ini`.

В конце выполняется:

```bash
composer update --no-dev --no-security-blocking --optimize-autoloader
```

Рабочая директория приложения внутри image:

```text
/app/site/backend/
```

### 3.5. Push в Nexus

После успешной сборки image пушится в Nexus:

```bash
docker push $REGISTRY_URL/$REGISTRY_REPO/$IMAGE_NAME:$IMAGE_TAG
```

### 3.6. Kubernetes deploy

Деплой всегда идет в namespace:

```text
stage
```

Pipeline создает namespace, если его нет:

```bash
kubectl create namespace stage --dry-run=client -o yaml | kubectl apply -f -
```

Дальше применяется Secret из подготовленного `.env`:

```bash
kubectl create secret generic back-mgmnt-microservice-secret \
    --from-file=.env=./app/.env \
    --namespace=stage \
    --dry-run=client -o yaml | kubectl apply -f -
```

### 3.7. Kubernetes-ресурсы `back-mgmnt-stage`

| Ресурс | Manifest | Назначение |
|--------|----------|------------|
| Secret | генерируется из `app/.env` | `.env` для backend pod |
| Service | `app/k8s/stage/app/service.yaml` | LoadBalancer для PHP-FPM, порт `9000` |
| Deployment | `app/k8s/stage/app/deployment.yaml` | PHP-FPM backend `back-mgmnt-microservice` |
| ConfigMap | `app/k8s/stage/nginx/configmap.yaml` | Nginx gateway config |
| Service | `app/k8s/stage/nginx/service.yaml` | LoadBalancer для Nginx gateway, порт `8081` |
| Deployment | `app/k8s/stage/nginx/deployment.yaml` | `frontend-nginx-gateway` |
| Deployment | `app/k8s/stage/redis/deployment.yaml` | Redis cache |
| Service | `app/k8s/stage/redis/service.yaml` | ClusterIP для Redis, порт `6379` |

### 3.8. Backend deployment

Основной deployment:

```text
back-mgmnt-microservice
```

Контейнер использует image из Jenkins:

```text
${IMAGE_FULL}
```

Порт контейнера:

```text
9000/TCP
```

`.env` монтируется из Secret:

```text
/app/.env
```

В deployment также настроены переменные Datadog и hostPath mount:

```text
/var/run/datadog
```

Readiness и liveness probes проверяют TCP-порт `9000`.

### 3.9. Nginx gateway

Deployment:

```text
frontend-nginx-gateway
```

Особенность: gateway сам работает на `nginx:1.25-alpine`, но статические файлы берет из собранного backend image через initContainer:

```text
copy-static
```

InitContainer запускается из `${IMAGE_FULL}` и копирует:

```text
/app/site/backend/public -> /shared/public
```

Nginx gateway:

- обслуживает backend public assets;
- проксирует PHP-запросы на `back-mgmnt-microservice.stage.svc.cluster.local:9000`;
- проксирует `/manager/` и часть `/assets/` на `manager-frontend.stage.svc.cluster.local`;
- использует ConfigMap `frontend-nginx-gateway-config`.

### 3.10. Redis

Redis деплоится отдельным deployment:

```text
back-mgmnt-redis
```

Image:

```text
redis:7-alpine
```

Redis запускается без persistence:

```text
--save ""
--appendonly no
```

Ограничение памяти:

```text
--maxmemory 256mb
--maxmemory-policy allkeys-lru
```

После применения manifests pipeline делает restart:

```bash
kubectl rollout restart deployment/back-mgmnt-redis -n stage
```

### 3.11. Rollout и rollback

Pipeline проверяет rollout двух deployment:

```bash
kubectl rollout status deployment/back-mgmnt-microservice -n stage --timeout=300s
kubectl rollout status deployment/frontend-nginx-gateway -n stage --timeout=300s
```

Если rollout не завершился, выполняется rollback соответствующего deployment:

```bash
kubectl rollout undo deployment/back-mgmnt-microservice -n stage
kubectl rollout undo deployment/frontend-nginx-gateway -n stage
```

### 3.12. Cleanup

После выполнения pipeline:

- удаляется локальный Docker image с Jenkins agent;
- удаляется временный `app/.env`;
- удаляется checkout `envs/`.

## 4. Сборка `maxline-manager`

### 4.1. Что собирается

Сборка собирает frontend `maxline-manager` как статический SPA и упаковывает его в Nginx image.

Основной Dockerfile:

```text
maxline-manager/k8s/Dockerfile
```

Контекст сборки:

```text
maxline-manager/
```

Итоговый image:

```text
nexus.maxline.by/docker-images-hosted/maxline-manager:<IMAGE_TAG>
```

### 4.2. Параметры Jenkins

| Параметр | Тип | Назначение |
|----------|-----|------------|
| `BRANCH` | Git branch | Ветка репозитория `maxline-manager` |
| `DEPLOY_ENV` | Choice: `stage`, `prod` | Окружение для build arg и выбора Kubernetes manifests |

### 4.3. Checkout

Исходники клонируются в:

```text
maxline-manager/
```

Репозиторий:

```text
git@bitbucket.org:maxlinecode/maxline-manager.git
```

Credentials:

```text
default-key
```

### 4.4. Docker build

Команда сборки:

```bash
docker build --no-cache \
    -t $REGISTRY_URL/$REGISTRY_REPO/$IMAGE_NAME:$IMAGE_TAG \
    -f maxline-manager/k8s/Dockerfile \
    --build-arg DEPLOY_ENV=$DEPLOY_ENV \
    maxline-manager/
```

Dockerfile состоит из двух stages.

### 4.5. Build stage

Base image:

```text
node:22-alpine
```

Подготовка package manager:

```bash
corepack enable
corepack prepare pnpm@10.28.1 --activate
```

Установка зависимостей:

```bash
pnpm install --frozen-lockfile
```

Выбор env-файла:

```bash
cp .env.${DEPLOY_ENV} .env
```

Сборка:

```bash
pnpm build
```

По `package.json` команда `build` запускает:

```bash
vite build
```

### 4.6. Runtime stage

Runtime image:

```text
nginx:1.25-alpine
```

В runtime image копируются:

| Источник | Назначение |
|----------|------------|
| `k8s/nginx.conf` | `/etc/nginx/conf.d/default.conf` |
| `/app/dist` из build stage | `/usr/share/nginx/html` |

Контейнер слушает:

```text
8080
```

### 4.7. Push в Nexus

После успешной сборки image пушится в Nexus:

```bash
docker push $REGISTRY_URL/$REGISTRY_REPO/$IMAGE_NAME:$IMAGE_TAG
```

### 4.8. Kubernetes deploy

Namespace выбирается из `DEPLOY_ENV`:

```text
stage или prod
```

Pipeline применяет manifests:

```bash
kubectl apply -f ./maxline-manager/k8s/$DEPLOY_ENV/configmap.yaml
kubectl apply -f ./maxline-manager/k8s/$DEPLOY_ENV/service.yaml
envsubst < ./maxline-manager/k8s/$DEPLOY_ENV/deployment.yaml | kubectl apply -f -
```

Deployment:

```text
manager-frontend
```

Image подставляется через:

```text
${IMAGE_FULL}
```

### 4.9. Kubernetes-ресурсы `maxline-manager`

Для `stage` используются:

| Ресурс | Manifest | Назначение |
|--------|----------|------------|
| ConfigMap | `maxline-manager/k8s/stage/configmap.yaml` | Nginx config `manager-frontend-config` |
| Service | `maxline-manager/k8s/stage/service.yaml` | ClusterIP service `manager-frontend`, порт `80 -> 8080` |
| Deployment | `maxline-manager/k8s/stage/deployment.yaml` | Deployment `manager-frontend` |

Service `manager-frontend` имеет тип:

```text
ClusterIP
```

Это важно: прямого LoadBalancer для manager frontend нет. Доступ к нему предполагается через Nginx gateway из сборки `back-mgmnt-stage`, который проксирует `/manager/` на:

```text
manager-frontend.stage.svc.cluster.local
```

### 4.10. Rollout и rollback

Pipeline проверяет rollout:

```bash
kubectl rollout status deployment/manager-frontend -n $DEPLOY_ENV --timeout=300s
```

Если rollout не завершился, выполняется rollback:

```bash
kubectl rollout undo deployment/manager-frontend -n $DEPLOY_ENV
```

### 4.11. Cleanup

После выполнения pipeline удаляется локальный Docker image с Jenkins agent.

## 5. Связь двух сборок

`back-mgmnt-stage` и `maxline-manager` связаны на уровне Kubernetes runtime.

`maxline-manager` деплоит отдельный SPA service:

```text
manager-frontend.stage.svc.cluster.local
```

`back-mgmnt-stage` деплоит Nginx gateway, который:

- принимает HTTP-трафик на LoadBalancer `10.10.1.179:8081`;
- обслуживает backend public files;
- отправляет PHP-запросы на `back-mgmnt-microservice`;
- отправляет `/manager/` на `manager-frontend`;
- отправляет часть root-level `/assets/...` на `manager-frontend`.

Поэтому для полноценной работы manager-интерфейса в stage нужны обе сборки:

1. `maxline-manager` должен быть собран и задеплоен как `manager-frontend`.
2. `back-mgmnt-stage` должен быть задеплоен с Nginx gateway config, который знает про `manager-frontend.stage.svc.cluster.local`.

## 7. Важные замечания

### 7.1. `maxline-manager` prod manifests

В pipeline `maxline-manager` есть выбор `DEPLOY_ENV=prod`, но в локальном репозитории есть только директория:

```text
maxline-manager/k8s/stage/
```

Если на Jenkins в нужной ветке также нет директории:

```text
maxline-manager/k8s/prod/
```

то запуск с `DEPLOY_ENV=prod` завершится ошибкой на этапе применения manifests.

### 7.2. `back-mgmnt-stage` зависит от env-репозитория

Сборка backend не самодостаточна: без `docker_maxline_by` она не получит:

- `.env`;
- `default_settings.php`.

Если checkout env-репозитория или копирование файлов упадет, Docker image не будет собран корректно.

### 7.3. `back-mgmnt-stage` содержит backend и public files

Один Docker image используется двумя способами:

- как PHP-FPM runtime для `back-mgmnt-microservice`;
- как источник public files для initContainer `frontend-nginx-gateway`.

Это значит, что изменение public assets в backend-репозитории требует нового деплоя `back-mgmnt-stage`, даже если PHP-код не менялся.

### 7.4. `manager-frontend` доступен через gateway

`manager-frontend` не публикуется наружу напрямую. Он доступен внутри namespace как ClusterIP service и используется Nginx gateway из `back-mgmnt-stage`.

### 7.5. Cleanup не удаляет image из Nexus

Post-step удаляет только локальный image на Jenkins agent. Tags в Nexus остаются и должны чиститься отдельной политикой или отдельным cleanup job.
